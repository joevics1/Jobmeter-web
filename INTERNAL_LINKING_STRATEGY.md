# JobMeter Internal Linking Strategy

## 1. The site's real architecture

JobMeter has seven content clusters, each with its own hub page and dynamic detail pages:

| Cluster | Hub | Detail pages | Approx. scale |
|---|---|---|---|
| Jobs | `/jobs` | `/jobs/[slug]`, `/jobs/[country]/[slug]` | thousands, DB-driven |
| Categories (location × role) | `/category` | `/category/[slug]` | hundreds, DB-driven |
| Companies | `/company` | `/company/[slug]` | hundreds, DB-driven |
| Blog | `/blog` | `/blog/[slug]` | dozens–hundreds, DB-driven |
| CV Templates | `/cv-templates` | `/cv-templates/[role]` | dozens–hundreds, DB-driven |
| Tools | `/tools` | 49 static routes under `/tools/*` | 49, fixed |
| Documents | `/documents` | `/documents/[type]/[country]` | dozens, DB-driven |

Before this pass, these were **seven separate silos**. Each hub linked down into its own detail pages, but almost nothing linked *sideways* between clusters, and the two sitewide chrome elements (homepage, footer) barely referenced most of them. That's the core problem: link equity generated by external backlinks or high-traffic pages (mostly the homepage and job listings) had no path into the Tools, CV Templates, or Blog clusters.

## 2. The model: hub-and-spoke + cross-cluster bridges

Two mechanisms, layered:

1. **Within a cluster** — every hub links to its children (already true), and every detail page links back to its hub and to 2–5 sibling pages (related tools, related categories, related blog posts). This is the "spoke" layer and is mostly what SEO people mean by "topic clusters."
2. **Between clusters** — every detail page also links out to the 1–2 *other* clusters a user would logically go to next. A CV template page should link to matching jobs and to interview prep. A blog post about salaries should link to the salary calculator and to job categories. A tool result page should link to the CV builder and to jobs. This is what actually makes "everything interconnected" rather than seven islands.

The two sitewide elements — **header/footer nav** and **homepage** — sit above both layers. They're the highest-authority pages on the site, so they should link to every hub, and every hub should be reachable in ≤2 clicks from the homepage.

## 3. What was broken (fixed in this pass)

- **Homepage** linked to `/resources`, `/privacy`, `/terms` — none of which exist (real routes: `/resource`, `/privacy-policy`, `/terms-of-service`). Your highest-authority page was leaking equity into 404s. Fixed, and added missing links to `/category`, `/tools`, `/cv-templates`.
- **Blog related-posts section** rendered the literal string "Related posts coming soon..." — never implemented. Every blog post dead-ended. Replaced with a real query (same category, falling back to most recent) plus a "Keep Exploring" block linking out to Jobs, Tools, and CV Templates.
- **CV template role pages** (`/cv-templates/[role]`, a large DB-driven cluster) had **zero outbound links** apart from the builder flow and CV history. Added a "Next Steps" block: matching jobs search, ATS review tool, interview practice, CV template hub, blog.
- **The 49 tool pages** had no shared cross-linking at all. Added `app/tools/layout.tsx`, which wraps every page under `/tools/*` automatically and appends sibling tools plus links to Jobs/CV Templates/Blog — one file, 49 pages fixed.
- **Footer** was a 7-link stub shown on most pages. Rebuilt into a 4-column mega-footer (Job Seekers / Career Tools / Resources / Company) so every cluster is one click away from anywhere on the site.
- **`/resource` hub** only had 4 generic cards and never linked to individual tools or CV templates. Added CV Templates as a fifth card and a "Popular Tools" row linking directly to 10 individual tool pages.
- Fixed dangling `/resources/[slug]` links in unused legacy components (`CategoryContent.tsx`, `components/resources/*`) so they don't reintroduce 404s if ever wired back in.
- Added `lib/toolsNav.ts` as a single source of truth for tool metadata (id/title/route/group), extracted from the existing `/tools` page data, so the footer, tools cross-link strip, and resource hub don't each hardcode their own copy that can drift out of sync.

## 4. Still worth doing (not done in this pass — needs a product decision or DB schema check)

- **`TimedJobPopup.tsx`** links its main CTA to `/apply-for-me`, which doesn't exist as a route (404 for real users). There's an unused `ApplyForMeQuiz.tsx` component that looks like it was meant to live there. Either build the page or remove/redirect the CTA — I didn't want to guess at unfinished product scope.
- **Category pages** (`/category/[slug]`) already have a `RelatedLinks` component driven by `related_locations_json` / `related_roles_json` from the DB — good. Worth also adding a link from each category page to the single most relevant tool (e.g., a "Kano" category page → cost-of-living or salary-benchmark tool) and to a matching blog post by tag, once those relationships are queryable.
- **Company pages** already link job↔company well (checked `/company/[slug]`). Consider adding a "jobs at similar companies in this category" cross-link once you have a sector field, and a link out to the relevant `/category` page for that company's main hiring location.
- **Header nav** only shows Jobs / Post Job / Documents / Tools / Resources / Settings — Blog, Category, and Company aren't in primary nav, only reachable via footer or internal links now. Worth a UX call on whether they belong in the header too, since footer links carry less crawl priority than header links.
- **`/companies` redirects to `/jobs`** in `next.config.js`, which looks like a leftover from before `/company` existed — redirecting to `/company` would preserve intent-matching for anyone (or any old backlink) hitting that URL.
- Blog posts have a `related_posts` DB column (`string[]`) that's currently unused — my fix ignores it and queries by category instead. If that column is meant to hold curated slugs, wiring it in as a priority source (before the category fallback) would let editors hand-pick related content.

## 5. Why this shape, not something else

- I didn't build a generic "related content" AI/algorithm — the DB fields for relatedness already exist in most tables (`related_categories`, `related_locations_json`, blog `category`/`tags`), so cross-links use those rather than inventing a new similarity system.
- I used shared layouts (`app/tools/layout.tsx`) instead of editing 49 files individually — one change point, consistent output, easy to extend later (e.g. per-tool tailored suggestions) without touching every page again.
- I extracted `lib/toolsNav.ts` instead of copy-pasting the tools list into the footer and layout — three places needed tool metadata; duplicating it three times is exactly how sites end up with stale/broken links again in six months.
